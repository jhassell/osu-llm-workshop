# For helpers: the first ten minutes

Carry this on a laptop or a printout. Order matters: the common fixes are first.

1. No terminal, or a terminal with only a `$`. Click in it, type `bash setup.sh`, Enter. If there is no terminal panel at all: the menu at the top left, Terminal, New Terminal.
2. The key prompt is waiting. Pasting does not show anything; that is on purpose. Paste once, press Enter once. If someone typed `bash setup.sh` into the key prompt, setup says so and asks again.
3. Setup chooses the endpoint from the key: a key starting `sk-or-` goes to OpenRouter, one starting `nvapi-` goes to NVIDIA's hosted endpoint, anything else is treated as the OSU workshop key from the card. The workshop address comes from `workshop-endpoint.txt` in their repository, or, if that is blank, from the instructor's current copy online, so an old copy of the repository finds it too.
   - "That looks like the OSU workshop key, but the workshop endpoint is not set up yet." Ask what they pasted. If it was an OpenRouter or NVIDIA key, the paste lost its first characters: copy the whole key and paste again. If it was the card key, tell the instructor: either the address is not published yet, or their Codespace could not download it.
   - "That key was not accepted." Nine times out of ten the paste caught a space or missed a character. `bash setup.sh --reset-key`, paste again from the card.
4. The check prints `reachable` and then `not reachable: HTTP 401` or `403`. The key was refused. `bash setup.sh --reset-key`, paste again.
5. The check prints `completion: (empty reply, twice)`. The model answered with no text, even after a retry with more room. Run the check once more. If it stays empty for several people, tell the instructor.
6. `not reachable` with a network error. The check runs in the Codespace, on GitHub's machine, so the laptop's wifi is not the path that failed, as long as the terminal still responds. If the browser tab lost its connection, VS Code shows a reconnecting message and nothing typed works: fix the laptop's wifi first. Otherwise read the error text: a name that cannot be resolved, a refused connection, or a timeout. Run the check again, and give the instructor the exact error line if it repeats.
7. `not reachable` with HTTP 429 or 503. The endpoint is busy. Wait thirty seconds and run the check again. If it persists, tell the instructor.
8. After `bash setup.sh --model <name>`, the check still names the old model. The labs and the check read only `.env`, so look at the model line in setup's last box; if setup reported an error, the model name is wrong for this endpoint. A Codespaces secret `LLM_MODEL` only matters to setup, and `--model` overrides it.
9. Someone pasted their own NVIDIA key and setup says "does not know that address or model" with HTTP 404 even though the model list loaded. The key was accepted; NVIDIA opens only some hosted models to a personal account. Setup's message names a model that works; `bash setup.sh --reset-key --model <that name>`. For other models they must ask help@build.nvidia.com to enable Public API Endpoints on their account, which is not a same-day fix.
10. Someone pressed 2 at setup's question and landed in OpenClaw before running the check. `/exit` or Ctrl+C closes it and lands at `$`; then `python 00_setup/check.py`. Pressing Enter (choice 1) also connects OpenClaw, without opening it. If setup said OpenClaw could not be connected, or OpenClaw later says it is not connected or its configuration was not accepted, `bash setup.sh --openclaw` writes it again and opens it; the reason is in `~/.osu-llm-workshop-openclaw.log`. The check and the lessons do not need OpenClaw, so the check comes first either way.
11. Trust Folder dialog never clicked. The terminal cannot start until it is. It is a blue button in the editor area, easy to miss behind a tab.
12. Codespace stuck on "Setting up your codespace" for more than five minutes. Go to github.com/codespaces, stop it, start it again. If that fails, delete it and create a new one from their repository; it builds in three minutes.
13. No GitHub account, or the template step was skipped. Pair them with a neighbor for the morning. A helper creates the repository and Codespace with them at the break.
14. After the instructor switches the room (`bash 00_setup/switch_backend.sh ...` on screen), every pasted key goes to that endpoint, so make sure people paste the key for it. To redo the paste after a switch, run the switch command again, not `bash setup.sh --reset-key`, which lets the key choose the endpoint again.

## The first exercise: the website

15. The site address shows the placeholder page, "This site is empty for now". Either the agent has not written `site/index.html` yet (look at its tool-call lines, or `ls site`), or the browser tab needs a refresh. If the agent wrote its pages somewhere else, have them type: `Put the pages in site/ at the top of the repository.`
16. The site address does not open, or the Ports tab shows port 8000 as Private. Right-click the port 8000 row, Port Visibility, Public. If their GitHub organization forbids public ports it stays private: the site still opens for them from the Ports tab, which is enough for today. If port 8000 is not in the Ports tab at all, `bash .devcontainer/site-public.sh` starts the server and makes it public; it prints nothing, so wait ten seconds and look again. What it did is in `~/.osu-llm-workshop-site.log`. The READY box shows `the Ports tab, port 8000` instead of an address whenever making the port public had not finished or failed; that alone is not a problem.
17. `python3 .devcontainer/site-check.py` fails. It names each file and what is wrong, never the text it matched. A link starting with `/` is the usual one: have them tell the agent `Use relative links only. Fix every page.` A symlink or anything shaped like a key: have the agent remove it, then look at how it got there. Run the check again after each fix. Warnings (scripts from other sites, very large files) do not stop it; they are for a person to look at.
18. `bash publish-site.sh` ends with a box that says `ONE STEP LEFT.`: GitHub did not let the Codespace turn Pages on. A one-time click in their repository on github.com: Settings, Pages, under Build and deployment set Source to Deploy from a branch, branch `gh-pages`, folder `/ (root)`, Save. Then `bash publish-site.sh` again. The first publish takes a minute or two to appear at `https://<owner>.github.io/<repo>/`.
19. `bash publish-site.sh` says the repository is private. On a free account Pages serves only public repositories. Their choice: make it public (Settings, General, Danger Zone, Change visibility, after looking at what is committed; `.env` and `mine/` never are), or skip publishing and download the `site` folder (right-click it in the file list, Download). Publishing is always their decision; never run the script for them.

What not to do: do not open, print or edit anyone's `.env` by hand, do not type a key for them on a shared screen, do not delete `mine/`, and do not run `publish-site.sh` for anyone. To see which settings `.env` holds without showing the key: `grep -o '^[A-Z_]*=' .env`.
